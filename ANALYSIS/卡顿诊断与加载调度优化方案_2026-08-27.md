> 日期：2026-08-27
> 适用工作区：`E:\1_project_E\model\RM_website`
> 目标：诊断引导页打字、照片墙、章节吸附、FOCUS 返回 timeline、远距离环视返回 timeline 五类已知卡顿，并给出加载调度与相机交接方案。
> 状态：本文已同步当前工作树的第一轮修复；历史探针运行在 Microsoft Edge headless + SwiftShader，资源先后和源码结构可作为证据，绝对帧率与长任务时长不能当成真实 GPU 的生产数据。

## 1. 结论先行

### 1.1 五类卡顿都能在当前实现中找到明确竞争源

1. **打字卡顿不是打字机本身首先造成的。** 当前程序先等待点云下载、点云几何创建、GPU 编译和首帧提交，之后才挂载引导页；引导页开始打字后，又立即并发加载 7 组 GLTF、解析约 17.14 MB 资产、生成机器人点云并执行整场景 `compileAsync`。每 34ms 一次的 React 打字更新正好和最重的主线程 / GPU 初始化重叠。
2. **照片墙不是单一图片太大，而是资源、解码、合成和滚动计算同时叠加。** 组件声明 12 张图但实际只有 6 张；现有 6 张压缩后约 12.44 MB，解码成 RGBA 约 173 MB。激活后 12 个 URL 同时进入页面、12 层都参与运动、每层各有桌面和移动端 spring，最大缩放到 13 倍，离开时还对整个舞台做最高 14px 的实时 blur。同时，底下的 Three.js 渲染循环没有停止。
3. **吸附末端的微卡是当前算法可以解释的。** 每个吸附动画帧都会遍历目标并调用 `getBoundingClientRect()`，随后同帧 `window.scrollTo()`；进入 26px 锁定半径且速度低于 90px/s 时，又会用一次精确 `scrollTo(attractor.top)` 完成最后跳变。页面还有多个独立 scroll/rAF 订阅者，读写时序没有统一。
4. **FOCUS 返回 timeline 的“双卡”同时包含串行动画和重复触发。** 当前先用 500ms 收起面板，再开始 1s 相机回飞；计时器启动回飞时却提前解除退出锁，而全局状态仍保持 `focus`，触控板惯性滚轮或同一触屏手势可以再次调用 `focus.exit()`，从中间姿态重启回飞。完成回飞的同一渲染帧又会切回 `scrub` 并让 timeline / lookAround 再写一次相机。
5. **远距离环视返回不是单纯“速度慢”。** 松手后固定停留 2s，再以 `blendOutSpeed: 1.6` 做渐近回程；按当前 0.002 收敛阈值，回程本身约需 3.88s，总计约 5.88s。timeline 在此期间冻结但保留旧 `velocity` 与 `autoHold`，交权后的第一帧可能恢复旧速度，形成第二个速度峰值；距离越远，固定时长内的位移变化越明显。

需要真实硬件复测：

- 任何 FPS 数字、某个长任务在用户电脑上的准确持续时间。

## 3. 当前加载链路为什么会卡住打字

### 3.1 实际执行顺序

| 顺序 | 源码位置 | 当前行为 |
| --- | --- | --- |
| 1 | `src/main.js` 1–32 | 主入口静态导入 Three、全部 3D 控制器、Intro 和三个 2D React islands；浏览器必须先解析整块主 JS |
| 2 | `src/main.js` 51–55 | 立即挂载照片墙、队员心声和联系渠道，即使用户还在 3D 前段 |
| 3 | `src/main.js` 80–103 | 创建 WebGL stage，等待 `arena_points.bin`，创建点云几何 |
| 4 | `src/main.js` 1433–1438 | 对 P0 场景执行 `compileAsync`，提交首帧并关闭 loading |
| 5 | `src/main.js` 1468–1470 | 此时才挂载打字引导页 |
| 6 | `src/main.js` 1475–1478 | 打字刚开始就调用 `prepareDeferredAssets()` |
| 7 | `src/main.js` 456–507 | `loadMany()` 并发加载 7 组 GLTF，配置场景并生成 Explore 机器人点云 |
| 8 | `src/main.js` 518–603 | 把所有对象加入场景并对完整场景再次 `compileAsync` |

`src/core/assetPipeline.js` 125–130 行的 `Promise.all` 是并发聚集点：

```js
const entries = await Promise.all(
  uniqueKeys.map(async (key) => [key, await load(key)]),
);
```

### 3.2 打字机自身的次要成本

位置：`src/components/intro-screen.tsx` 96–141 行。

当前每个字符通过 `setProgress` 触发一次 React render，目标节奏为 `CHAR_MS = 34`。只有几十个字符时，这本身通常不应造成肉眼可见的停顿；先移走 P1 竞争，再决定是否重写打字机。

若移走 P1 后目标电脑仍有打字抖动，再做第二层优化：

1. 把完整行和 segment DOM 只创建一次。
2. 用一个 `requestAnimationFrame` 根据 `performance.now()` 计算当前字符数，而不是为每个字符建立独立 timeout。
3. 只在字符数实际变化时更新文本；刷新率上限 30Hz 即可满足 34ms 节奏。
4. 更彻底的方案是通过 `ref.textContent` 更新两个固定文本节点，避免整个引导组件重渲染。
5. `prefers-reduced-motion` 直接显示完整文案。

不要先花时间微调 `CHAR_MS`。主线程被 5 秒级任务占住时，把 34ms 改成 40ms没有意义。

## 4. 目标加载调度

### 4.1 新的阶段表

| 页面状态 | 用户看到的内容 | 允许下载 | 允许主线程 / GPU 工作 | 明确禁止 |
| --- | --- | --- | --- | --- |
| HTML / INTRO 首帧 | 深空背景、第一行文字 | Intro 小入口、字体；不创建视频播放器 | 只挂载 Intro 和必要事件 | 创建 WebGL、挂载 2D islands、解析 GLTF |
| TYPING | 两行英文逐字出现 | `arena_points.bin`；可在空闲时预取 3D chunk | 只做轻量文本更新；点云 ArrayBuffer 暂存内存 | 创建 50k 点几何、贴 GPU、编译场景、创建 iframe |
| CTA REVEAL | 中文说明与按钮 | 若 3D chunk 未到，继续预取 | 创建 stage、构建 P0 点云；工作超过一帧时显示 `PREPARING ARENA…` | 同时解析七组 P1 |

| EXPLORE 首帧 | 场地点云与切换面板 | 核心组 `arena + timeline + robot`，最多 2 路；之后是编队组 | 每次只配置 / 编译一个组；空闲预算内继续 | 7 组 `Promise.all`、4 个视频播放器 |
| EXPLORE 稳定后 | 用户旋转、点击、切换 | 编队组 `hero + engineer + infantry + sentry`；按需 `dart` | 逐资产贴图解码、逐组 compile；监控长任务 | 在同一帧 add 全部场景并全量 compile |
| SCAN | 场地扫描转换 | 不启动新的低优先级大下载 | 核心组必须 ready；只做状态动画 | 边扫描边解码大贴图 |
| SCRUB / 3D TIMELINE | 相机时间轴 | 本地视频海报、小型元数据；可保留 DNS/preconnect | 不创建 Bilibili iframe | 播放器脚本、广告/统计、视频流与 3D 同时争用 |
| PHOTO WALL | 赛事照片 | 当前层 + 后 2 层响应式图片 | 解码窗口控制在 2–3 张；3D 降到 0–15fps | 12 张同时解码、整舞台实时 blur |
| 2D MEDIA 接近视口 | 影像记录 | 主视频 iframe；高光仍为 facade | 最多一个新播放器初始化 | 四个播放器一起启动 |
| 2D ARCHIVE | 文档阅读 | 当前章节附近图片 | 停止 Three 循环 | 背景中持续 60fps WebGL |
| RETURN 走廊 | 重返 3D | 无新大资源 | 先恢复低频渲染，画布可见后恢复全速 | 首次可见帧才重新编译 shader |

### 4.2 就绪门槛必须拆开

当前只有一个粗粒度的 `deferredAssetsReady`，并且它等到 7 组资产、机器人编队和整场景 compile 全部完成。改为四个明确 Promise：

```js
const pointDataReady = preloadArenaPointData();
const pointCloudReady = prepareArenaPointCloud(pointDataReady);
const scanCoreReady = prepareAssetGroup(["arena", "timeline", "robot"]);
const squadReady = prepareAssetGroup(["hero", "engineer", "infantry", "sentry"]);
```

状态门槛：

- Intro 可以立即显示，不依赖任何上述 Promise。
- CTA 可以出现，不依赖点云；点云未就绪时按钮显示准备状态。
- ASSEMBLE 只依赖 `pointCloudReady`。
- EXPLORE 可以只依赖 P0 点云。
- EXPLORE → SCAN 依赖 `scanCoreReady`；若编队在扫描画面必须可见，则同时依赖 `squadReady`，否则使用已准备的低成本占位层。
- `dart` 和其他 Explore 备用点云按第一次切换或空闲时准备，不阻塞 SCAN。

| --- | --- | --- |

- 保留 `dns-prefetch`；是否保留 `<link rel="preconnect">` 用真实网络测试决定。
- 预取本地封面图片。
- 不请求 Bilibili player HTML，不请求视频流。

## 8. FOCUS / 环视返回 TIMELINE 的“双卡”诊断与修复

### 8.1 先区分“真的掉帧”和“相机时序不连续”

修复前两条返回路径里没有直接发起新模型加载；源码首先暴露的是动画分段、重复触发和相机控制权交接问题。它们即使在每帧都低于 16.7ms 时，也会因为速度曲线出现两个阶段或两个峰值而被感知成“卡两次”。最终 trace 仍需同时检查图片 decode、shader 和 long task，但不能只看 FPS 后就判定问题不存在。

| 结论 | 源码证据 | 置信度 |
| --- | --- | --- |
| FOCUS 修复前是 500ms UI 淡出后再开始 1s 回飞 | `src/main.js` 1137–1150；`src/focus/focusController.js` 3–4、230–247 | 高，固定时序 |
| FOCUS 回飞期间可被再次触发 | timer 回调在 1147 行先置空，状态要等 691–695 行的完成回调才变为 `scrub` | 高，存在明确重入窗口 |
| 触屏同一手势会持续请求退出 | `src/main.js` 1258–1263 未像 EXPLORE 分支那样把 `swipeAccum` 设为负无穷 | 高，输入路径明确 |
| FOCUS 完成帧存在两套相机写入 | 1467 行 `focus.update()` 可在回调中切到 `scrub`；随后 1560–1567 行同帧执行 timeline / lookAround | 高，逐帧顺序明确 |
| 环视松手至完全归位约 5.88s | `2s + ln(1 / 0.002) / 1.6`，参数位于 `src/config.js` 263–272 | 高，数学上确定 |

| 是否还叠加 GPU / 图片解码长任务 | 静态源码无法给出用户机器上的帧耗时 | 待真实 trace |

### 8.2 FOCUS 为什么有时会真正“退出两次”

当前时序如下：

```text
t = 0.0s  第一批 wheel/touch -> exitFocus()
          focusExitTimer 非空，面板开始淡出，相机不动
t = 0.5s  timer 回调：先把 focusExitTimer 设回 null
          再调用 focus.exit()，1s 回飞开始；全局 state 仍是 focus
t = 0.5–1.5s
          触控板惯性 wheel 或仍在移动的手指再次进入 exitFocus()
          因 state === focus 且 timer === null，第二个 500ms timer 被接受
t ≈ 1.0–2.0s
          第二次 focus.exit() 从中间姿态重新捕获 startPos，回飞曲线重启
```

`focusController.exit()` 本身也没有 `mode === "exiting"` 防重入。鼠标每次只产生一个离散滚轮脉冲时不一定触发，所以问题表现为“有时候”；带惯性的触控板和长触屏手势更容易复现。

即便没有重入，当前设计仍有两个可感知阶段：面板单独收起 0.5s，然后相机才移动 1s。相机回飞完成时，`focus.update()` 先写入终点并同步触发 `setState("scrub")`；同一帧后半段随即执行 `timeline.update()` 与 `lookAround.update()`。timeline 在 FOCUS 期间没有更新，但旧 `velocity` 和 `autoHold` 仍被保存，因此第二次写入可能不是刚才的精确终点。

### 8.3 远距离环视为什么更明显

环视状态机位于 `src/timeline/lookAroundController.js`：

```text
idle -> entering -> active -> holding(2s) -> exiting(~3.88s) -> idle
```

`advanceTransition()` 使用指数逼近，并在剩余误差小于 0.002 时才结束。当前 `blendOutSpeed = 1.6`，所以退出阶段的理论时间是：

```text
t = -ln(0.002) / 1.6 ≈ 3.88s
松手后总时间 = hold 2.00s + return 3.88s ≈ 5.88s
```

这条曲线与世界空间距离无关：近处和 30m 上限附近都用同一时间常数。远处回程在前段每帧位移更大，尾段仍保留相同的渐近拖尾，于是“先停住、再快速拉回、末尾又像顿一下”的感觉更强。

主循环在环视非 idle 时调用 `timeline.update(delta, true)`，因此 progress、`velocity`、`autoHold` 全部冻结。`lookAround.update()` 在某帧末尾才把 mode 改为 idle，timeline 到下一帧才恢复；如果接管前恰好有较大的正向或负向滚轮速度，第一帧会恢复这笔旧输入，形成第二个速度峰值。这也解释了为什么同样从远处返回不是每次都同样明显。

### 8.4 目标状态机：一次请求、一个时钟、一个相机 owner

两个返回路径应共享以下约束：

1. 一次手势只能创建一次返回事务；锁从请求当帧持续到回飞完成，不能在“相机刚开始飞”时释放。
2. UI 淡出与相机回飞从同一个触发点并行执行，不再用 500ms `setTimeout` 串联。若视觉上确需 UI 领先，只允许 80–120ms 的同一动画时钟偏移，并且期间仍处于 locked 状态。
3. 每一渲染帧只能有一个 camera owner：`focus`、`lookAround`、`timeline` 或 `handoff` 四选一。
4. 交权保留 timeline progress，但丢弃接管前的滚轮瞬时速度和 `autoHold`；恢复时从正常 `autoRate` 开始，不能在数秒后重放旧输入。
5. 完成回飞的那一帧是 handoff 帧，不再调用下一个控制器写相机；下一帧才恢复 timeline。

目标时序：

```text
FOCUS active
  -> focus exiting [立即锁定；面板淡出与相机回飞并行]
  -> handoff [一帧，只保留 focus 写出的终点]
  -> SCRUB / timeline [progress 不变；速度归一为 autoRate]

LOOK active
  -> look returning [松手立即开始；固定时长、距离感知]
  -> handoff [一帧]
  -> SCRUB / timeline [progress 不变；不恢复旧 wheel velocity]
```

```js
const distance = startPosition.distanceTo(targetPosition);
```

### 8.6 诊断埋点与验收

在现有无截图探针中增加以下事件，时间使用同一个 `performance.now()`：

- `focus-exit-requested`、`focus-exit-started`、`focus-exit-completed`，每次事务带同一个 id。
- `look-return-started`、`look-return-completed`，记录起点距离、四元数夹角和计算出的 duration。
- 每帧记录 `cameraOwner`；开发模式断言同一 frame id 最多一个 owner 调用相机写入。
- handoff 前后记录 timeline progress、velocity、autoHold；恢复首帧必须是归一化速度，而不是接管前速度。
- 记录相机每帧位置差与旋转角差；若回程中出现第二个局部速度峰值，直接关联到事务 id 和 owner 变更。

复测矩阵：

1. FOCUS 中用鼠标滚轮单击式退出。
2. FOCUS 中用触控板快速滑动并保留惯性尾包。
3. FOCUS 中用触屏长上滑，越过阈值后继续移动手指。
4. timeline 正向高速、反向高速、接近静止三种状态下分别进入 FOCUS 再退出。
5. 环视分别停在接近 `distanceMin` 与 `distanceMax`、小角度与大角度位置后松手。
6. 环视回程中主动再次按下拖拽，确认这是一次新的显式事务，而不是旧事务抖动。

通过标准：每个手势只有一个 `started` 和一个 `completed`；任一帧最多一个 camera owner；FOCUS 的 UI 与回飞同时开始；环视松手到归位不超过计算出的 1.1s 上限；handoff 后没有第二个非用户输入速度峰值。long task 门槛单独统计，不能用“没有 long task”替代上述时序验收。

## 9. Three.js 在 2D 页面下仍持续运行

位置：`src/main.js` 1311–1422 行；`src/core/stage.js` 166–182 行。

修复前 `stage.start()` 一旦调用，就通过 `renderer.setAnimationLoop` 持续更新：

- 点云和备用模型点云。
- 背景环。
- 引导投影。
- 灯光和机器人动画。
- orbit / timeline / focus。
- composer render。

进入照片墙和档案后，1422 行仍执行 `stage.render()`。这会与图片 decode、CSS 合成、滚动吸附和 iframe 竞争。

建议给 stage 增加明确生命周期：

```text
FULL       3D 可交互，正常 animation loop
THROTTLED  照片墙覆盖，最多 15fps或仅滚动时重绘
PAUSED     2D 档案完全覆盖，setAnimationLoop(null)
WARMUP     RETURN 接近视口，先恢复并提交一帧
```

触发依据使用页面状态和 IntersectionObserver，不使用固定 scrollY 魔数。暂停前保留最后一帧画布；恢复时重置 Clock，避免第一帧 `delta` 过大。`visibilitychange` 隐藏标签页时也必须暂停。

验收：档案正文可见且 3D 画布完全被覆盖时，Performance 面板不应再出现持续 WebGL frame；返回走廊出现前恢复一帧，用户不能看到黑画布或首次 shader 编译闪顿。

当前落地定位：

| 位置 | 当前行为 |
| --- | --- |
| `src/core/stage.js`，`pause()` | 调用 `renderer.setAnimationLoop(null)` 并停止 `THREE.Clock`，避免恢复第一帧出现巨大 delta |
| `src/core/stage.js`，`resume()` | 重新启动 `Clock` 并恢复原 animation loop callback |
| `src/core/stage.js`，`running` getter | 供调试钩子确认当前渲染循环状态 |
| `src/main.js`，`enterUnitArchive()` | 进入 `state === "end"`、文档滚动释放和档案 reveal 启动后调用 `stage.pause()` |
| `src/main.js`，`returnToTimeline()` | 从 2D 返回 3D 前先 `stage.resume()`，再恢复 `scrub` 状态 |
| `src/main.js`，`visibilitychange` | 标签页隐藏时暂停；回到页面且不在 2D 档案时恢复 |
| `window.__ENTERPRIZE_DEMO__.renderLoopActive` | Playwright / 手工调试可直接读取 animation loop 是否运行 |

## 10. 资产格式与传输优化

调度修复优先于压缩。当前本地高速请求已经能卡，说明单纯减小下载不能消除解析 / 上传聚集；但调度稳定后仍应做以下 P1 优化：

### 10.1 GLTF 与几何

- 对 `arena`、`timeline`、四类机器人分别测量 transfer、JSON parse、buffer parse、texture decode、GPU compile，不按总文件大小猜瓶颈。
- 评估 GLB 合包以减少依赖请求，但不要把所有场景合成一个不可分阶段加载的大 GLB。
- 对重复机器人几何使用共享 geometry/material；红蓝双方用 Y 轴 `Math.PI` 旋转和材质参数化，不用负 scale 复制。
- Meshopt / Draco 必须用目标设备测解码 CPU。网络慢时压缩收益大，低端 CPU 上可能把下载等待换成主线程解码。

### 10.2 贴图

- 当前最大 P1 单资源是 sentry PNG，约 4.44 MB；timeline 的 `hit.png` 约 2.01 MB；arena PNG 约 1.57 MB。
- 优先转 KTX2/Basis，并按实际材质决定 ETC1S 或 UASTC；验证色彩空间、alpha 和发光材质。
- 贴图尺寸按屏幕实际投影上限裁切，不保留看不见的超高分辨率。
- 预编译仍需分组；KTX2 减少显存和上传压力，但首次 transcoder 初始化也要避开打字阶段。

### 10.3 点云

- `arena_points.bin` 约 600 KB，网络不是当前大头；重点是不要在打字活跃期创建 BufferGeometry、上传 attribute 和 compile。
- 若未来点数增大，可在 Worker 中做数据解包 / 归一化，再把 ArrayBuffer transfer 回主线程；Three 对象和 WebGL 上传仍留在主线程。
- 首屏只保留能支持当前镜头的点数，完整点云可在 EXPLORE 稳定后提升。

## 11. 主入口拆包与 2D islands 延迟挂载

当前生产构建主 JS 约为 1.10 MB raw / 310 KB gzip。`src/main.js` 顶部静态导入 Three、3D 控制器、Intro、照片墙、testimonial 和 glowing cards；即使用户只看第一行打字，也要先解析整套运行时。

建议的入口边界：

```text
intro-entry
  ├─ Intro 最小 UI / 文案 / point-data fetch
  └─ dynamic import arena-runtime

arena-runtime
  ├─ Three stage / point cloud / scan / timeline / focus
  └─ dynamic import archive-entry near document transition

archive-entry
  ├─ unitSite 基础交互
  ├─ dynamic zoom-parallax near photo wall
  ├─ dynamic testimonials near voices
  └─ dynamic glowing channels near contacts
```

目标不是追求更多 chunk 数，而是让“打字首帧”不解析 Three 和照片墙，让“只看 3D 的用户”不创建 2D React trees。

拆包验收：

- 首个 Intro chunk 不包含 Three、照片墙和 Bilibili player。
- 3D runtime 在第一段文字已绘制之后再下载 / 执行。
- archive islands 只有接近对应板块时才出现在 Network 和 React tree。
- 页面状态机入口仍唯一；动态 import 不得各自注册重复 wheel / resize 监听器。

## 12. 移动端必须做能力分级

`src/main.js` 73–74 行当前明确让移动端运行完整 3D；`src/core/stage.js` 9–15 行只把 coarse pointer 的 pixel ratio 上限降到 1.5。这不足以覆盖低端手机的 GPU、内存和热降频差异。

推荐根据能力和首秒实测分级，而不是只看 UA：

| 等级 | 建议 |
| --- | --- |
| High | DPR 上限 1.5–2；50k 点；Bloom 开启；完整编队 |
| Medium | DPR 上限 1.25；点数降到 25k–35k；降低星数和发光；分批出现编队 |
| Low | DPR 1；关闭 Bloom；静态 / 低频点云；不自动加载备用模型和视频 |
| Fallback | WebGL 初始化失败、持续低帧或内存过低时，直接进入 2D 档案并保留返回说明 |

等级应参考 `deviceMemory`、`hardwareConcurrency`、WebGL 能力和前 60–120 帧的实际耗时。不要把 automated SwiftShader 结果映射成用户等级。

### 14.1 每次优化都做 A/B

| A/B | A | B | 用来回答的问题 |
| --- | --- | --- | --- |
| TYPE-01 | 当前 P1 在打字期 | 打字期禁止 P1 | 打字抖动是否主要来自资产准备竞争 |
| TYPE-02 | React 每字符 state | rAF / 固定文本节点 | 移走 P1 后打字机自身是否仍值得重写 |
| MEDIA-01 | 4 iframe 初始存在 | 全部 facade | 视频脚本对 Intro 和主线程的实际影响 |
| WALL-01 | 原图 + 12 层 + blur | 响应式 6 图 + 3 图窗口 + overlay | decode、合成和滤镜各削减多少 |
| SNAP-01 | 每帧测布局 + 26px 锁 | 原生 proximity + 显式 scene marker | 尾段微跳和落点偏差是否同时消失 |
| FOCUS-01 | 500ms 串行等待 + timer 锁 | 同时淡出/回飞 + 事务锁 + 单帧 handoff | 双阶段和重复回飞是否消失 |
| LOOK-01 | 2s hold + 指数长尾 + 旧速度恢复 | 松手即固定时长返回 + 归一化 resume | 远距离第二个速度峰值是否消失 |
| WEBGL-01 | 2D 下持续 render | archive 下 pause | 滚动 long task、功耗和风扇占用变化 |

### 14.2 建议门槛

- 打字期间：不出现超过 100ms 的 long task；字符间隔 p95 不高于目标节奏 + 20ms，最大异常间隔低于 100ms。
- EXPLORE：第一帧先稳定显示，再开始 P1；任一单组资产准备不得阻塞输入超过 100ms。
- 照片墙：无无效图片；桌面解码驻留不高于 64 MB，移动端不高于 32 MB。
- 吸附：没有 JS 尾段修正；布局稳定后，scene 视觉焦点落在约定安全线或中心 ±2px。
- FOCUS / 环视：一次手势对应一次返回事务；每帧最多一个 camera owner；handoff 后不恢复旧 wheel velocity。
- 环视：松手立即开始回程，按距离计算的总回程不超过 1.1s；曲线中不出现非用户输入的第二个速度峰值。
- 2D 档案：Three 完全遮挡时 animation loop 为暂停状态。
- 视频：到 2D 影像区接近视口之前，`player.bilibili.com/player.html` 请求数为 0。
- 布局：CLS 需要排除开发 loading/intro 切换后重新测；固定媒体都必须有 `aspect-ratio` 或明确尺寸。

### 14.3 真实硬件复测

至少覆盖：

1. Windows 桌面独显 / 1440×900。
2. Windows 核显或省电模式。
3. iOS Safari 或 Android Chrome 中档设备。
4. 鼠标滚轮、触控板、触屏三种输入。
5. 正常网络和 Fast 3G / 4G 模拟，分别看 transfer 与 parse 的占比。

使用浏览器 Performance 面板保留 trace，标记 Intro typing、EXPLORE enter、SCAN enter、FOCUS exit、LOOK return、PHOTO WALL enter、SNAP settle 七段。自动检查通过只代表没有明显回归，最终视觉和手感仍由用户在本地页面验收。

## 15. 完成定义

只有同时满足以下条件，才算本轮卡顿修复完成：

- 用户看见第一段打字时，点云只在网络层预取，P1 GLTF 没有开始解析 / 编译。

- 2D 正文期间 WebGL 不在后台持续全速渲染。
