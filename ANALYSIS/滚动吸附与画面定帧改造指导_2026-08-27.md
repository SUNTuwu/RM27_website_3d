> 状态：P0 已在当前工作树实施；行号会随格式化变化，后续定位以文件名、函数名、选择器和 `data-*` 锚点为准。

## 1. 结论先行

当前方案不应继续靠调 `impulseGain`、`stiffness`、`lockRadiusPx` 修补。推荐直接改为下面四层，各层只负责一件事：

```text
浏览器原生滚动
  -> CSS Scroll Snap proximity 只负责靠近关键画面时落位
  -> IntersectionObserver 只负责进入画面后的渐显/激活
  -> position: sticky 只负责少数重点画面的停留
  -> object-position 只负责图片主体在裁切框中的位置
```

固定决策：

1. 删除 `setupChapterSnap()` 对 `wheel`、`touchmove` 和 `window.scrollTo()` 的全局接管。
2. 档案长页面使用原生 `scroll-snap-type: y proximity`，不使用全局 `mandatory`。
3. 不再用 `.archive-chapter`、`.archive-media` 这类宽泛选择器自动推断吸附点；只有显式标记了 `data-snap-scene` 的画面才参与吸附。
4. 章节很长时，吸附目标是章节里的“视觉画面”或标题锚点，不是整个章节容器的 `top`。
5. 想让一张好看的画面停久一点，使用 sticky stage；吸附只负责“停在哪里”，不负责“停多久”。
6. 图片主体偏高或偏低时修改 `object-position`，不要通过移动整页吸附位置来补偿图片裁切。
7. **`#unit-reveal` 固定不使用 sticky。** 它只做一次 center snap 与入场 reveal，随后跟随文档自然离场，不额外拉长滚动轨道。

本决定取代 `卡顿诊断与加载调度优化方案_2026-08-27.md` 第 7.2 节“保留当前弹簧并重写计算路径”的保守方案。用户已经明确否定当前手感，继续保留自定义滚动的收益不足以抵消维护成本。

## 2. 先区分四种看起来相似的效果

| 名称 | 用户感受到的效果 | 正确技术 | 是否适合当前档案页 |
| --- | --- | --- | --- |
| 吸附 snap | 松开滚轮/触控板后，页面靠近某幅构图并稳定落位 | CSS Scroll Snap | 适合，但只标记少量关键画面 |
| 翻页 page deck | 一次输入强制切到完整下一屏 | `mandatory` snap 或离散页状态机 | 不适合整份长档案，只适合独立的短序列 |
| 渐显 reveal | 画面进入视口时文字、图片依次出现 | IntersectionObserver + CSS transition | 适合；当前已有基础实现 |
| 定帧/停留 hold | 用户继续滚动，画面仍钉在视口中一段距离 | 外层滚动轨道 + `position: sticky` | 只用于横幅或后续明确批准的少数整屏画面；兵种 reveal 不使用 |

很多作品站所谓“滚动翻页渐显”，实际是三者组合：自然滚动靠近 scene，原生 snap 完成最后落位，scene 进入视口中部时触发 stagger reveal；需要强调的画面再额外 sticky。它不是每一帧都用 JavaScript 把窗口拉向某个 DOM 顶部。

## 3. 修复前实现到底做了什么

### 3.1 参数与入口

| 修复前位置 | 原职责 | 原问题 |
| --- | --- | --- |
| `src/config.js` 8–32 行，`VISUAL_CONFIG.chapterSnap` | 定义宽泛目标选择器、惯性、吸引半径、弹簧刚度和锁定阈值 | 参数同时承担设备手感、目标选择和最终落位，互相耦合 |
| `src/ui/unitSite.js` 139–299 行，`setupChapterSnap(root)` | 拦截 wheel/touch，自行积分速度、选择目标并逐帧 `scrollTo` | 重写了浏览器原生惯性，且每帧布局读取后立即写滚动位置 |
| `src/ui/unitSite.js` 501–509 行 | 在档案 UI 初始化时启用自定义吸附 | 整个档案模式全局生效 |
| `src/styles.css` 121–137 行 | 文档模式只隐藏滚动条和限制过渡 overscroll | 当前没有 CSS `scroll-snap-type`，实际手感完全由 JS 控制 |

当前主循环是：

```text
wheel delta
  -> preventDefault
  -> delta * impulseGain 写入 velocity
  -> 每帧遍历全部 target
  -> 每个 target 调 getBoundingClientRect()
  -> 选择当前 scrollY 附近最近的 target
  -> 弹簧修改 velocity
  -> window.scrollTo(next)
  -> 距离 < 26px 且速度 < 90px/s 时再精确 scrollTo(target.top)
```

这并不是常见的网页原生吸附，而是一个页面级自定义物理滚动器。

### 3.2 “按 DOM 顺序解析”实际意味着什么

`src/config.js` 当前选择器为：

```js
targets: [
  ".archive-chapter",
  ".archive-media",
  ".archive-banner",
  "#unit-reveal",
]
```

`src/ui/unitSite.js` 148 行把它们拼成一个选择器传给 `querySelectorAll()`。返回结果按文档树顺序排列，并不是先返回全部 `.archive-chapter`，再返回 `.archive-media`。当前实际顺序为：

| 顺序 | 实际元素 | 当前对齐依据 |
| --- | --- | --- |
| 1 | `#archive-hero` | 整个章节边界顶部 |
| 2 | `#archive-media` | 整个媒体区边界顶部 |
| 3 | `#archive-team` | 整个章节边界顶部 |
| 4 | `#archive-banner` | 72vh 横幅边界顶部 |
| 5 | `#archive-units` | 整个章节边界顶部 |
| 6 | `#unit-reveal` | 兵种大字模块边界顶部 |
| 7 | `#archive-join` | 整个长章节边界顶部 |
| 8 | `#archive-return` | 返回章节边界顶部 |

DOM 顺序只影响数组顺序、平局和 `targets[0]` 的特殊逻辑。真正选择目标的是 `nearestAttractor()` 中的“吸引半径内绝对距离最近者”，不是“滚动方向上的下一个目标”。因此会出现：

- 两个目标距离较近时，中途切换吸引对象。
- 已经越过前一个目标后，前一个目标仍可能从上方继续拉扯。
- 快速触控板输入可能跨过一个目标，再被另一个目标反向修正。
- `targets[0]` 被硬编码成 3D 返回走廊例外；只要 DOM 前面插入新的命中元素，例外就会错误地套到另一个目标上。

结论：问题不只是“DOM 顺序可能不准”，而是目标本身没有视觉语义，算法也没有明确的“下一页”状态。

### 3.3 已有测量证据

`ANALYSIS/performance-audit-current.json` 106–120 行记录了一次 1440×900 的诊断：

- 测量时目标 `top`：5966.39px。
- 最终 `scrollY`：5884px，与首次测得位置相差约 82.39px。

## 4. 为什么会吸得太高或太低

### 4.1 当前永远把元素 border-box 顶部对齐视口顶部

当前计算可简化为：

```text
elementDocumentTop = element.getBoundingClientRect().top + scrollY
landingScrollY = elementDocumentTop
```

它没有表达以下任何信息：

- 视觉主体在元素内部的哪个位置。
- 视觉主体应该落在视口的 40%、50% 还是 60%。
- 顶部是否需要留出安全空间。
- 元素是 72vh、100vh 还是一个远高于视口的长章节。

例如 `.archive-banner` 当前 `min-height: 72vh`。把它的顶部钉在视口 0% 后，横幅中心位于视口 36%；如果真正想要居中构图，横幅顶部应该落在约 14vh，而不是视口最顶端。这就是典型的“吸得太高”，并非弹簧参数问题。

### 4.2 媒体区的 top 不是媒体画面的 top

`src/archive.css` 508–540 行中：

- `.archive-media::before` 先占据 90–170px 的浅到深过渡。
- 后面 `.archive-wrap` 仍有通用顶部 padding。
- 主视频还在标题和 label 之后。

吸到 `#archive-media` 顶部，只能保证先看到渐变走廊，不能保证标题或主视频构图正确。正确做法是分别标记“媒体标题”和“主视频”中的关键画面，而不是吸整个 section。

### 4.3 长章节没有唯一正确的 top

`#archive-units` 和 `#archive-join` 都远高于一屏。章节顶部只是内容开始位置，不代表章节中最值得停留的画面。尤其 `#archive-units` 内又嵌套 `#unit-reveal`，父章节和子画面同时成为吸附点，会形成竞争。

### 4.4 图片裁切偏差与页面落位偏差被混在一起

`.archive-banner__bg` 使用 `object-fit: cover`，但没有设置专属 `object-position`；`.archive-return__bg` 已经使用 `object-position: center 38%`。如果主体在图片里偏上或偏下，应像 RETURN 一样为图片设焦点，而不是改 section 的吸附 top。

```css
.archive-banner__bg {
  object-position: var(--focus-x, 50%) var(--focus-y, 50%);
}
```

### 4.5 布局在首次测量后仍可能变化

潜在来源包括字体就绪、图片解码、iframe lazy load、响应式单列切换、FAQ 展开以及照片墙退出。自定义代码取得一个 top 并不意味着这个坐标之后仍然成立。原生 CSS snap 会基于当前布局工作，但仍应通过 `aspect-ratio`、明确尺寸和字体占位尽量消除 layout shift。

## 5. 推荐架构

### 5.1 原生滚动与 proximity snap

根滚动容器规则放在 `src/styles.css` 现有 `html.is-document-mode` 规则附近：

```css
html.is-document-mode:not(.is-document-transitioning) {
  --snap-safe-top: clamp(48px, 8svh, 88px);
  --snap-safe-bottom: clamp(28px, 5svh, 56px);
  scroll-snap-type: y proximity;
  scroll-padding-block: var(--snap-safe-top) var(--snap-safe-bottom);
}

html.is-document-transitioning {
  scroll-snap-type: none;
}

[data-snap-scene] {
  scroll-snap-stop: normal;
}

[data-snap-align="start"] {
  scroll-snap-align: start;
}

[data-snap-align="center"] {
  scroll-snap-align: center;
}

@media (prefers-reduced-motion: reduce) {
  html.is-document-mode {
    scroll-snap-type: none;
    scroll-behavior: auto;
  }
}
```

关键点：

- 使用 `proximity`，让用户仍能阅读长内容和停在非关键位置。
- 使用 `scroll-snap-stop: normal`，允许触控板快速越过画面；不要全局设为 `always`。
- `is-document-transitioning` 期间关闭 snap，避免与 `src/main.js` 824–865 行的 3D→照片墙过渡争夺滚动位置。
- 不设置全局 `scroll-behavior: smooth`；章节导航点击时按需调用 smooth，减少多个平滑器叠加。

### 5.2 显式 scene，而不是选择器猜测

吸附意图直接写在对应 DOM 上。吸附目标自身必须是稳定、无 transform 动画的盒子；当前 `.archive-head.reveal` 会先 `translateY(36px)` 再回到 0，不能直接兼任 snap target。应在标题前放置独立 marker：

```html
<span
  class="snap-marker"
  data-snap-scene="team-intro"
  data-snap-align="start"
  aria-hidden="true"
></span>

<header class="archive-head reveal">
  ...
</header>

<section
  class="archive-banner"
  id="archive-banner"
  data-snap-scene="manifesto"
  data-snap-align="center"
>
  ...
</section>
```

如果视觉焦点不是现成元素的中心，就在视觉焦点处放置一个语义明确的 marker：

```html
<span
  class="snap-marker"
  data-snap-scene="unit-lineup-focus"
  data-snap-align="center"
  aria-hidden="true"
></span>
```

marker 应放在希望对齐的内容位置，而不是通过一个全局像素常量猜偏移。它可以是正常文档流中的 1px 元素：

```css
.snap-marker {
  display: block;
  width: 1px;
  height: 1px;
  pointer-events: none;
}
```

### 5.3 精确画面位置的计算模型

设计一幅吸附画面时，应先指定两个点：

1. 元素内部的焦点 `anchorRatio`，0 是顶部、0.5 是中心、1 是底部。
2. 焦点在视口中的期望位置 `viewportRatio`。

理论落位为：

```text
documentAnchorY = elementTop + elementHeight * anchorRatio
desiredScreenY = safeTop + usableViewportHeight * viewportRatio
landingScrollY = documentAnchorY - desiredScreenY
```

CSS 的 `start`、`center`、`end` 能覆盖大部分情况；需要更特殊的位置时移动 marker，而不是在滚动循环里加 `+ 83px`、`- 12vh` 之类补丁。

## 7. 如何让一张好看的画面“停在那里”

### 7.1 只需要松手后落位：使用 snap

适用于整屏海报、横幅、章节开场。为视觉容器添加 `data-snap-scene`，选择 `start` 或 `center`，再通过固定比例和 `object-position` 确定构图。

### 7.2 需要用户继续滚动但画面不走：使用 sticky hold

结构：

```html
<section class="archive-hold" data-hold-scene="manifesto">
  <div
    class="archive-hold__frame"
    data-snap-scene="manifesto"
    data-snap-align="start"
  >
    <!-- 完整视觉画面 -->
  </div>
</section>
```

```css
.archive-hold {
  position: relative;
  min-height: 160svh;
}

.archive-hold__frame {
  position: sticky;
  top: 0;
  min-height: 100svh;
  overflow: clip;
}
```

用户滚过额外的 60svh 时，画面仍留在视口；这才是“停留时间”。不要通过提高弹簧刚度或反复拉回滚动位置制造停留。

sticky 只建议用于 2–3 个高潮，不能套到每个章节，否则页面会像演示文稿，长文阅读和快速跳转都会变慢。

`#unit-reveal` 不属于本节的 sticky 候选。它本身已经通过大字排版和逐行显现建立高潮；继续钉住会让用户误以为这一屏还有操作或信息等待完成，也会延迟进入后面的兵种内容。实现时保留现有 reveal 进度或改为 scene observer 均可，但外层高度保持内容所需的自然高度，不增加 `140svh`、`180svh` 一类 hold track。

### 7.3 图片主体位置：使用焦点参数

为每张重要图片设置焦点，而不是只写 `object-fit: cover`：

```html
<section class="archive-banner" style="--focus-x: 52%; --focus-y: 42%">
  <img class="archive-banner__bg" ... />
</section>
```

```css
.archive-banner__bg {
  object-fit: cover;
  object-position: var(--focus-x, 50%) var(--focus-y, 50%);
}
```

判断顺序：

1. 整个 section 在视口中太高/太低：改 snap align 或 marker。
2. section 位置正确，但图片里机器人头部被切掉：改 `object-position`。
3. 桌面正确、移动端错误：为移动端设置单独焦点变量，不要共用一个像素偏移。

## 8. 渐显应该如何配合吸附

当前 `src/ui/unitSite.js` 15–59 行的 `setupReveals()` 已经采用常见结构：IntersectionObserver 检测 `.reveal`，进入后加 `.is-in`；`src/archive.css` 2286–2297 行用 opacity + translateY 完成动画。基础方向正确，可保留。

当前不足是 threshold 0.12 会让长元素在画面还没落位前就完成渐显。建议拆成两级：

1. 普通正文继续使用一次性 `.reveal`，进入视口即显示。
2. `data-snap-scene` 使用独立 scene observer；当 scene 的中心 marker 进入视口中部带状区域时添加 `.is-scene-active`。
3. scene 内部子项通过 `--reveal-order` 依次出现，不用每个子项注册独立 scroll/rAF。
4. 动画只使用 opacity、transform 或 clip-path，不使用会改变布局的 height/width，也不对整屏持续 blur。

建议触发区：

```js
new IntersectionObserver(onSceneChange, {
  rootMargin: "-38% 0px -38% 0px",
  threshold: 0,
});
```

这相当于在视口中部保留约 24% 高的激活带。吸附画面进入该区域时触发，落位与渐显会在心理上形成同一个动作。具体 38% 需要视觉验收，不应写成散落在多个组件中的魔数。

对于 sticky scene，如果需要随滚动连续交叉淡化，只给该 scene 计算一个 0–1 progress，再由所有子层共享；不要为每张图、每行字建立独立 spring。

## 10. 调试方式：不要再靠肉眼猜 top

开发模式增加 snap debug overlay，仅在 URL 或 HTML 开关启用：

```text
视口顶部安全线          safeTop
视口视觉中心线          usable viewport center
视口底部安全线          safeBottom
每个 data-snap-scene    outline + scene id + align
当前落位误差            actual marker screenY - desired screenY
```

建议调试开关：`<html data-debug-snap>`，生产构建默认不出现。每次落位后记录：

| 字段 | 含义 |
| --- | --- |
| `sceneId` | 当前显式画面 ID |
| `align` | start / center |
| `markerDocumentY` | marker 的文档坐标 |
| `desiredScreenY` | 期望屏幕坐标 |
| `actualScreenY` | 实际屏幕坐标 |
| `errorPx` | 两者差值 |
| `layoutStable` | 最近 250ms 是否发生 ResizeObserver / layout shift |

只有 `layoutStable` 为真时才评价吸附误差；否则应先修尺寸占位，不能继续调 offset。

## 11. 验收标准

### 手感

- 鼠标滚轮、Windows 精密触控板和触屏都保留浏览器原生惯性。
- 用户可以在长章节任意位置停留，不会被强制送到章节顶部。
- 接近显式 scene 时才吸附，快速滚动可以越过普通 scene。
- 输入结束后不出现反向回拉、尾段跳一下或 1 秒以上缓慢爬行。
- 不存在文档模式全局 wheel `preventDefault()`。

### 位置

- 1440×900、1366×768、768×1024、390×844 分别验收，不以单一桌面视口定参数。
- start scene 的标题落在顶部安全线内；center scene 的视觉焦点落在安全视口中心 ±2px。
- 横幅和返回页的图片主体不因 cover 裁切丢失；通过 `object-position` 调焦点。
- 字体、首图、lazy iframe 就绪后重新进入同一 scene，构图不漂移。
- 导航点击和自然滚动停在同一位置。

### 渐显与定帧

- 普通 `.reveal` 不阻塞阅读；scene reveal 在视觉焦点进入中部激活带时开始。
- `#unit-reveal` 中心落位后自然显现、自然离场，不出现 sticky 停留或额外空滚动距离。
- sticky 画面进入、停留、离开三个阶段连续，没有空白帧或突跳。
- 开启 `prefers-reduced-motion` 后关闭 sticky scrub、平滑跳转和 snap，所有内容直接可见。

### 3D/2D 交接

- `src/main.js` 的 `is-document-transitioning` 期间 snap 保持关闭。
- `.unit-site` 的 `margin-top: -100svh` 只允许在 `html.is-document-mode` 下启用；Intro、EXPLORE、SCAN 和 3D timeline 阶段不得露出 `WHO WE ARE // 我们是谁`。
- 3D→照片墙→档案首屏在 `is-document-transitioning` 期间不被 hero 吸附提前拉走，转场结束后才允许 start snap 稳定落位。
- 位于档案顶部继续向上滚动，仍能到达 `scrollY <= 1` 并返回 3D 时间轴。
- 照片墙已有 320svh sticky track 不与档案 snap 互相争夺。

## 12. 不建议采用的方案

- 不继续提高/降低 `stiffness` 猜手感；目标定义错误时参数无法修正构图。
- 不给所有 section 统一 `scroll-snap-align: start`；长章节和 72vh 横幅不存在同一种正确对齐。
- 不使用 `scroll-snap-type: y mandatory` 覆盖整份档案；会困住长内容、FAQ 和触屏用户。
- 不引入第二套全局平滑滚动库。照片墙已经有 Framer Motion 和自己的 scroll progress，再叠 Lenis/ScrollTrigger 类全局循环只会增加所有权冲突。
- 不使用固定的绝对 `scrollY` 魔数；页面内容、字体和视口变化都会让它失效。
- 不把图片主体裁切问题伪装成页面 offset 问题。

## 13. 最终建议

这次改造的关键不是“找到更准的选择器”，而是让每个好看的画面拥有明确的设计语义：

```text
这是哪个 scene
它的视觉焦点在哪里
焦点应落在视口哪里
只是松手后对齐，还是需要继续滚动时停留
桌面与移动端是否使用同一个构图
```

当这些信息写进 DOM 与 CSS 后，浏览器可以负责滚动，IntersectionObserver 可以负责入场，sticky 可以负责停留。页面不再需要一个不断猜测“最近 DOM 顶部”的弹簧系统。
